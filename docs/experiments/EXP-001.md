## Question and hypothesis

Can `black-forest-labs/FLUX.2-klein-base-4B` load, perform image editing, complete a tiny paired edit-LoRA training cycle, save an adapter, and reload it for inference on the Supervisor's free Kaggle GPU? Can the Base-trained adapter execute with `black-forest-labs/FLUX.2-klein-4B` distilled inference?

The hypothesis is feasibility under documented low-memory settings. [BFL training guidance](https://docs.bfl.ai/flux_2/flux2_klein_training) lists an NVIDIA GPU with 12 GB VRAM and 32 GB RAM as its Klein 4B Base training minimum, while [BFL's worked LoRA guide](https://huggingface.co/blog/black-forest-labs/flux-2-klein-lora) describes a run under 24 GB VRAM on an RTX 4090. Neither establishes performance on this Kaggle account. The [Base model card](https://huggingface.co/black-forest-labs/FLUX.2-klein-base-4B) verifies the model ID, image-edit capability, and Apache-2.0 license. [NVIDIA's CUDA guide](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/mathematical-functions.html) places native BF16 at compute capability 8.0+, so a runtime with capability 7.5 must use an evidence-backed non-BF16 path.

## Reproducible harness

Source: [Kaggle smoke-test script](../../notebooks/exp001_flux2_klein_kaggle_smoke.py). It is a single CLI artifact because dependency installation and model execution need separate Python processes; it contains ordered audit, preflight, Base load, Base edit, tiny training, Base adapter reload, and optional distilled compatibility stages. It does not bundle model weights or real photos.

In an authenticated Kaggle GPU notebook, enable internet and GPU, make the script available as a notebook input or in `/kaggle/working`, and run:

```python
!python /kaggle/working/exp001_flux2_klein_kaggle_smoke.py --audit-only
!python /kaggle/working/exp001_flux2_klein_kaggle_smoke.py
```

The first command audits without downloads. The second starts with another audit and stops before model download if GPU or scratch checks fail. The script writes durable evidence to `/kaggle/working/exp001/`; model weights use `/tmp/hf-cache` and the AI Toolkit checkout uses `/tmp/exp001-ai-toolkit`. Save or download `/kaggle/working/exp001/` before the session ends. The script measures actual disks and mounts before downloading.

The script looks for an optional `HF_TOKEN` in Kaggle Secrets or environment variables only if supplied; it never prints or stores the token. The public model is queried for access and file sizes before weights download. It pins [AI Toolkit](https://github.com/ostris/ai-toolkit) to commit `a8dfcf7d7e2b38ccc7b2fb68ece9c6358e61e7a7`, records installed packages, constrains pip to the observed Kaggle Torch/Torchvision/Torchaudio builds, and stops if Torch or CUDA changes. This avoids AI Toolkit's current manager path, which selects its own Torch/CUDA stack. The dataset uses the paired `control_path` format documented by [BFL's edit-LoRA recipe](https://huggingface.co/blog/black-forest-labs/flux-2-klein-lora).

## Intended tiny configuration

- Three deterministic 512×512 Pillow shape pairs, with matching `reference/` and `target/` names and target-side instruction captions. No hairstyle data.
- Single GPU `cuda:0`; 20 steps; batch size 1; 512 resolution; AdamW 8-bit; learning rate `1e-4`; LoRA linear rank/alpha 16/16 and conv 8/8. These are smoke-test settings, not selected production hyperparameters.
- FP16 on the observed T4 because its compute capability is 7.5. `torch.cuda.is_bf16_supported()` reporting true is recorded but does not establish native BF16 Tensor Core acceleration. AI Toolkit `quantize`, `low_vram`, and gradient checkpointing are enabled from the documented low-memory direction. The actual runtime must prove compatibility.
- Base edit uses seed 1977, 512×512, 20 inference steps, guidance 4.0, and the prompt in the script. Distilled test, only if scratch permits, uses four steps and guidance 1.0.
