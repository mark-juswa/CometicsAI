# EXP-001 — FLUX.2 Klein free-GPU feasibility

**Progress: EXP-001 BF16 stability gate complete. BF16 classification: FINITE TRAINING VERIFIED. Overall feasibility: YELLOW.** Prepared 2026-09-21; last updated 2026-09-22. FP16 produced NaN loss, while the controlled BF16 retry produced finite loss for three probe steps and all 20 confirmation steps. Its checkpoint saved and loaded into a fresh Base pipeline. Distilled compatibility remains untested.

## Question and hypothesis

Can `black-forest-labs/FLUX.2-klein-base-4B` load, perform image editing, complete a tiny paired edit-LoRA training cycle, save an adapter, and reload it for inference on the Supervisor's free Kaggle GPU? Can the Base-trained adapter execute with `black-forest-labs/FLUX.2-klein-4B` distilled inference?

The hypothesis is feasibility under documented low-memory settings. [BFL training guidance](https://docs.bfl.ai/flux_2/flux2_klein_training) lists an NVIDIA GPU with 12 GB VRAM and 32 GB RAM as its Klein 4B Base training minimum, while [BFL's worked LoRA guide](https://huggingface.co/blog/black-forest-labs/flux-2-klein-lora) describes a run under 24 GB VRAM on an RTX 4090. Neither establishes performance on this Kaggle account. The [Base model card](https://huggingface.co/black-forest-labs/FLUX.2-klein-base-4B) verifies the model ID, image-edit capability, and Apache-2.0 license. [NVIDIA's CUDA guide](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/mathematical-functions.html) places native BF16 at compute capability 8.0+. The T4's BF16 execution was therefore treated as an experiment, not assumed native acceleration.

## Reproducible harness

Source: [Kaggle smoke-test script](../../notebooks/exp001_flux2_klein_kaggle_smoke.py). It is a single CLI artifact because dependency installation and model execution need separate Python processes; it contains ordered audit, preflight, Base load, Base edit, tiny training, Base adapter reload, and optional distilled compatibility stages. It does not bundle model weights or real photos.

In an authenticated Kaggle GPU notebook, enable internet and GPU, make the script available as a notebook input or in `/kaggle/working`, and run:

```python
import subprocess, sys

probe = subprocess.run(
    [sys.executable, "-c", "import torch; assert torch.cuda.is_available()"],
    check=False,
)
assert probe.returncode == 0, "The kernel-selected child process has no CUDA"
subprocess.run([sys.executable, "/kaggle/working/exp001_flux2_klein_kaggle_smoke.py"], check=False)
```

The assertion proves that a fresh child process from the notebook kernel's selected executable sees CUDA. The harness starts with another audit and stops before model download if GPU or scratch checks fail. It writes durable evidence to `/kaggle/working/exp001/`; model weights use `/tmp/hf-cache` and the AI Toolkit checkout uses `/tmp/exp001-ai-toolkit`. Save or download `/kaggle/working/exp001/` before the session ends. The script measures actual disks and mounts before downloading.

The script looks for an optional `HF_TOKEN` in Kaggle Secrets or environment variables only if supplied; it never prints or stores the token. The public model is queried for access and file sizes before weights download. It pins [AI Toolkit](https://github.com/ostris/ai-toolkit) to commit `a8dfcf7d7e2b38ccc7b2fb68ece9c6358e61e7a7`, records installed packages, constrains pip to the observed Kaggle Torch/Torchvision/Torchaudio builds, and stops if Torch or CUDA changes. This avoids AI Toolkit's current manager path, which selects its own Torch/CUDA stack. The dataset uses the paired `control_path` format documented by [BFL's edit-LoRA recipe](https://huggingface.co/blog/black-forest-labs/flux-2-klein-lora).

## Intended tiny configuration

- Three deterministic 512×512 Pillow shape pairs, with matching `reference/` and `target/` names and target-side instruction captions. No hairstyle data.
- Single GPU `cuda:0`; 20 steps; batch size 1; 512 resolution; AdamW 8-bit; learning rate `1e-4`; LoRA linear rank/alpha 16/16 and conv 8/8. These are smoke-test settings, not selected production hyperparameters.
- The initial T4 trial used FP16 and produced NaN loss. The controlled retry used BF16 for training only and produced finite loss. `torch.cuda.is_bf16_supported()` reporting true does not establish native BF16 Tensor Core acceleration. AI Toolkit `quantize`, `low_vram`, and gradient checkpointing remained enabled.
- Base edit uses seed 1977, 512×512, 20 inference steps, guidance 4.0, and the prompt in the script. Distilled test, only if scratch permits, uses four steps and guidance 1.0.

## Failures, retries, and conclusion

The original scheduler stack matched upstream AI Toolkit issue [#835](https://github.com/ostris/ai-toolkit/issues/835): a FLUX.2 Klein job with `timestep_type: weighted` omitted `noise_scheduler`, retained AI Toolkit's generic `ddpm` default, and reached Diffusers `FlowMatchEulerDiscreteScheduler.set_timesteps`, which requires `mu` whenever `use_dynamic_shifting` is true. Adding only `train.noise_scheduler: "flowmatch"` correctly routed training through `CustomFlowMatchEulerDiscreteScheduler.set_train_timesteps`; the missing-`mu` error did not recur.

The loop then completed all 20 configured steps, and timer output confirms the backward and optimizer-step paths executed. However, the console printed `loss is nan` once per step even though the progress renderer displayed `loss: 0.000e+00`. The checkpoint is loadable and inference executes, proving serialization and adapter-loader compatibility only. A checkpoint produced from non-finite loss is not evidence of successful learning. Per the instructed stop condition, no precision, optimizer, quantization, dtype, model, dataset, or GPU change was attempted.

## Controlled BF16 stability test

Source: [BF16 stability script](../../notebooks/exp001_bf16_stability.py). It reuses the existing model cache, toolkit revision, synthetic pairs, scheduler, optimizer, learning rate, resolution, batch size, quantization, checkpoint save dtype, and LoRA settings. The only numerical change is training dtype from `float16` to `bf16`.

The script runs three steps in an isolated output folder and records each raw loss. Any non-finite loss, execution error, or OOM stops the test. Only three finite losses permit a fresh 20-step run with the same settings, FP16 checkpoint save, and fresh FP16 Base adapter load. It does not perform distilled testing, application work, dataset work, or another compatibility adjustment.

The attempted launch recorded `bf16_executed: false` and stopped before trainer initialization with:

```text
FileNotFoundError: [Errno 2] No such file or directory: '/kaggle/working/exp001/environment.json'
```

No three-step run occurred. There are no BF16 losses, timing, VRAM measurements, checkpoints, or adapter reload results. The error concerns missing setup evidence and does not show whether BF16 resolves the FP16 NaN.

The Supervisor then reran the unchanged probe after restoring the original environment audit, preflight, synthetic pairs, and pinned AI Toolkit setup. The full supplied [console log](EXP-001-bf16-console.log) and parsed [result JSON](EXP-001-bf16-result.json) are preserved here. The re-audit confirmed two T4 GPUs, PyTorch `2.10.0+cu128`, and CUDA `12.8`; training remained on GPU 0. AI Toolkit was pinned to commit `a8dfcf7d7e2b38ccc7b2fb68ece9c6358e61e7a7`. The generated configuration changed only `train.dtype` from `float16` to `bf16`; checkpoint save dtype remained `float16`.

The first three raw losses were `7.396e-03`, `7.976e-03`, and `7.069e-03`. All 20 confirmation losses were finite, from `5.932e-03` to `2.625e-01`. The 20-step run measured **32.808075 seconds per step** and **13,531 MiB** whole-GPU peak. AI Toolkit logged backward and optimizer steps, saved `/kaggle/working/exp001/training_bf16_20step/exp001_tiny_edit/exp001_tiny_edit.safetensors` at **46,223,600 bytes**, and Diffusers loaded that adapter into a fresh FP16 Base pipeline. The BF16 adapter was loaded but no BF16-adapter inference was performed in this focused retry. The earlier FP16-produced adapter inference is a separate observation.

Projected from the measured 20-step BF16 timing, excluding setup and checkpoint overhead: **500 steps 4.557 hours; 1,000 steps 9.113 hours; 1,500 steps 13.670 hours**. These are projections, not measured longer runs. The 20-step smoke test establishes numerical execution and serialization, not hairstyle quality or long-run stability. The absence of native BF16 Tensor Core acceleration on T4 is consistent with the large slowdown relative to the invalid FP16 run, but that causal explanation was not independently profiled. No architecture decision or additional training was made.

**Exactly one recommended next action:** the Project Lead should review the measured BF16 speed and remaining distilled compatibility gap before authorizing any further experiment.
