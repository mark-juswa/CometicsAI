# MOBILE-02B inspected integration plan

2026-10-03, baseline `a58a895`, branch `codex/mobile-02`. Supervisor explicitly authorizes real authenticated generation and folds MOBILE-02A manual visuals into final device acceptance. This documents the smallest existing-system integration, not a new architecture/design exercise.

## Confirmed source behavior

BeautyCore `lib/auth.ts` signs a seven-day JWT in `beautycore_session`, HttpOnly, SameSite=Lax, Secure in production. Login verifies the database password and sets that cookie; session reads the current database user; logout deletes the cookie. AI adapter reads the current database user and requires Client on every operation, independently of old JWT role claims. Mutations require Origin equal to the request's application origin. Upstream is server-configured loopback HTTP only, with allowlisted paths; cookies/session data are never forwarded upstream.

Native plan: use SDK 57 global Expo fetch with `credentials: include`, direct JSON login (no redirects) and the existing OS cookie jar. Never read/store the cookie in JS. Native mutations supply the configured application origin, with loopback hosts canonicalized to localhost exactly as the inspected NextURL implementation does before Origin comparison; browser requests retain browser-controlled Origin. Verify a follow-up `/api/auth/session` immediately after login, then a protected catalog; fail clearly rather than assume cookie persistence. Verify native navigation/session and logout manually. Existing browser/session/role/Origin behavior is unchanged. If actual Android proves cookies unreliable, stop and record the specific failure before selecting an additive adaptation.

## Exact boundary

Mobile configurable `EXPO_PUBLIC_API_BASE_URL` is the BeautyCore application origin. Methods use `/api/auth/login`, `/api/auth/session`, `/api/auth/logout`, `/api/ai/features`, `/api/ai/features/{feature}/styles`, `/api/ai/features/{feature}/generate`. Generation multipart has exactly `image` and `style_id`. SDK 57 installs Expo fetch globally; its encoder rejects the old RN local URI descriptor before transport, so native uploads use the existing expo-file-system File blob. A regression test exercises the installed encoder directly. Settings connectivity uses session reachability and protected catalogs because BeautyCore has no health route. No direct FastAPI health or generation fallback is permitted.

Current root launcher starts BeautyCore on loopback 3000 and private FastAPI on loopback 8000 through existing signed Kaggle discovery. MOBILE-01 launcher instead owns a mock FastAPI on 0.0.0.0:8001, so an additive authenticated mobile launcher mode is demonstrably required. It reuses authorized USB reverse for 3000/8081, verifies the existing BeautyCore auth boundary, starts only Expo with application origin process env, and never owns/stops root BeautyCore/FastAPI/Kaggle. Existing legacy helper mock mode remains for old launcher tests. LAN cannot reach the root loopback binding; refuse that mode clearly rather than expose FastAPI or modify root startup. Normal mobile batch chooses authenticated mode. No new public server secret variable.

## Generation safety and results

One in-memory generation operation across features, started synchronously before async multipart preparation, survives component rerender/navigation. No Query mutation retry and no automatic POST retry. Use the existing browser's no-fixed-generation-deadline behavior, preserving backend Hair/Makeup 180s and Nails 300s configurable remote budgets. Reads/auth have a bounded 12s deadline. Display service/style and elapsed wall time, no percentages. Block draft changes, duplicate Generate and logout while in flight. A success must be a completed, non-mock result with valid inline PNG/JPEG, selected style ID and dimensions. Mock/placeholder results cannot pass live acceptance.

The manual generation contract has no job ID/status endpoint or idempotency key. Response loss, timeout, malformed output, 5xx and uncertain 409 are ambiguous, so retain a global uncertainty lock and explain operator verification is needed before another request. Do not invent a status endpoint or retry automatically. Definitive pre-dispatch validation/auth errors permit manual correction/retry. An explicit operator-confirmed-ended action may release ambiguity, never silently release on Back/Reset/Start Over.

Returned inline image becomes the generated comparison; original remains a local URI. Share uses the supported native sharing sheet with a temporary app-cache file; Android Save uses the system Storage Access Framework folder chooser, grants access only to the chosen directory and handles cancellation/write failure. iOS uses supported legacy MediaLibrary add-only permission with explicit denial/settings handling. The installed Expo Go lacks ExpoMediaLibraryNext, so no import of that module remains. Cache files are cleaned after use; only an explicit Save persists to the selected folder/photos library. No photo/GPU log or server internals in product UI.

## Acceptance still required

Actual Client login, subsequent session/catalog, navigation persistence, logout and denied anonymous calls; one real Android Hair/Makeup/Nails result with timings and Nails inference_path; redesigned UI/Back/gallery/result/Save/Share on the phone; invalid login/image/style, API/AI failure, safe manual retry and duplicate prevention. Mock/local tests are supporting evidence, not real GPU acceptance. No full conversational Consultation or automatic MOBILE-02C work.
