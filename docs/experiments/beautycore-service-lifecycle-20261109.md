## Delivered workflow

- Existing appointments now support In Progress and No-Show, with shared badges and filters. Start Service and Mark Customer Arrived enforce assignment/administrator permissions and a backend eligibility window. Arrival protects a confirmed booking from automatic no-show even if the service starts later. Start records actual arrival/start timestamps without replacing scheduled time.
- Stop Service presents Service Completed, Client Did Not Attend, Service Cancelled and Other. Outcomes require confirmation; completion uses the existing product-recording form. Other stores an explanation/history event without changing status. An attended/started service cannot become no-show. Completion/cancellation records an end/outcome timestamp and releases its reservation through the established transaction.
- No-show preserves the appointment, original schedule/details and payment history. It cannot be started, completed, deleted or ordinarily edited. An administrator may restore/reschedule to a future valid time; the database rechecks staff qualifications, working hours and conflicts. Original no-show events remain in the history.
- Tracking and activity tables store timestamps, actor IDs, source, explanations and status changes. Existing API mutations identify the authenticated account; automatic events identify the system process. Old appointments get history only for new events; past activity is not invented.
- The database sweep checks a 30-minute grace period using UTC instants and the original scheduled time, excludes arrived/started work, and serializes with stylist and appointment locks. It is idempotent and processes bounded batches. Earlier overdue records before policy installation are excluded from automatic conversion.
- npm start and npm run dev include the backend worker with ten-second checks and retry/single-flight/shutdown handling. npm run worker:no-shows can run separately. Appointment/availability requests catch up missed work. Visible portals and booking availability refresh every ten seconds and immediately after local changes. A sleeping/stopped host cannot execute timers; catch-up runs when it returns, or an always-running standalone worker can maintain wall-clock checks. No new cloud scheduler or hosting settings were changed.
- Confirmed reservations stay fixed at 90 minutes. Running work has a rolling near-term hold (at least its scheduled reservation) until it stops, so immediate overlap is rejected while unrelated later bookings remain possible. Released current slots begin at the next future whole minute and still require a full 90-minute fit in working hours. Qualification, Available to Work and atomic double-booking checks remain enforced.
